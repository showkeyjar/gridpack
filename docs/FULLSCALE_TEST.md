# 全量测试报告（本机 ERA5 等数据）

日期：2026-10-15　被测版本：0.3.0 → 0.3.1

## 一、测试范围

本机 `D:\code\ai\CRPS\data` 下的 ERA5 数据共 **834 个 `.nc` 文件、356.6 GB**：

| 目录 | 文件数 | 磁盘 |
|---|---|---|
| `era5_wind_raw` | 408 | 222.4 GB |
| `era5_2t_raw` | 204 | 90.8 GB |
| `era5_tp_raw` | 204 | 35.8 GB |
| `era5_oos_raw` | 18 | 7.7 GB |

另有非 ERA5 格点数据：`cw-rain/data/raw/cml/cml.nc`(4.3 GB)、`radar.nc`(181 MB)，
以及 GEFS 的 `.grib2` 缓存。

**为什么不做全量压缩**：D 盘仅剩 81 GB，全量压缩产物需 150 GB 以上，
按实测 14 MB/s 也要约 20 小时。因此采用「**全文件覆盖扫描 + 代表性整文件端到端**」：

1. **覆盖扫描**：对**每一个** ERA5 文件取 3 个时次做主变量编解码，逐字节校验。
   834/834 个文件全部跑到（耗时 1223 s）。
2. **整文件端到端**：对差异最大的若干文件走完整 `compress → verify → decompress → 再校验`。

## 四、暴露的问题与修复

### 问题 1（严重，静默丢精度）：`detect_lattice` 未屏蔽符号位

`lattice.py` 计算指数时写成 `u >> 23`，把符号位一起算进了指数：负浮点数的 `exp`
会被多算 256。于是 `E_max = min(tz(sig) + exp - 150)` 会**偏大**，
`v / 2**E` 不再是整数，`np.rint` 把结果就近取整 —— **静默变成有损**。

复现（`cml.nc` 的 `tsl`）：取值只有 `{-3.0, 10.0}`，正确 E 应为 0；
bug 下算出 E=1，`-3.0 / 2 = -1.5` 被 `rint` 成 `-2`，还原成 `-4.0`。

ERA5 全部 834 个文件之所以没暴露，是因为 `E_max` 取的是全体最小值，
而 ERA5 每个文件里总有更小的正数贡献了正确的 `E_max`，负数的错误贡献被 `min` 掩盖。

**修复**：指数改为 `(u >> 23) & 0xFF`（float64 同理 `& 0x7FF`），
并新增 `verify_lattice()` 逐块回代确认 `v / 2**E` 确为整数，不通过就退回保序映射。
两道保险叠加后，这类"指数算大"的错误不可能再静默通过。

修复后：`rsl`/`tsl` 正确判定为无格点（E=None）走保序映射，往返 `ok=True`。

### 问题 2（崩溃）：0 维数据集触发 `IndexError`

`compress_file` 里 `fc = ... else max(d.shape[0], 1)`，遇到 0 维标量数据集
（`radar.nc` 的 `crs`）时 `d.shape[0]` 抛 `IndexError: tuple index out of range`。
同时 `parts` 里 0 维数据集记 `n=0`，解码端会算出空数组。

**修复**：按 `ndim` 分三支处理（≥2 / ==1 / ==0），0 维记 `n=1`，
标量赋值取 `[0]`。修复后 `radar.nc` 整文件通过（28.83x，逐字节一致）。

### 问题 3（内存）：`detect_lattice` 峰值达数据量的 17.5 倍

实测：对 24.9M 个值（95 MB）的单个分块，`detect_lattice` 峰值内存 **1662 MB**。
原因是全程用 int64 且每步 `np.where` 都产生临时数组。在机器已有负载时，
`200001_10u.nc` 直接 `MemoryError` 失败。

**修复**：改为按 400 万值分块统计（峰值与数组总大小无关），float32 路径改用 int32；
`codec` 侧对 `MemoryError` 做兜底，退化为保序映射而不是让整份文件失败。
修复后 `200001_10u.nc` 整文件通过（3.94x，逐字节一致）。

### 问题 4（能力缺口）：不支持 GRIB2，且报错不友好

对 `.grib2` 文件报 `OSError: Unable to synchronously open file (file signature not found)`——
这是 h5py 的底层报错，用户无法据此判断"格式不支持"。
本机 GEFS 缓存有约 2.5 万个 `.grib2` 文件（约 25 GB），目前完全用不上。

**建议**：在 `compress_file` 入口做魔数嗅探，非 HDF5 时抛出明确的
`UnsupportedFormatError`；GRIB 支持需另行接入 `cfgrib`/`eccodes`。
